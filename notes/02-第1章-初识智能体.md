## 一、什么是智能体

> 通过传感器感知环境、并**自主**通过执行器采取行动以达成目标的实体。

「自主」是重量级的两字：它区分了「智能体」和「脚本」。脚本按人写死的路径走，智能体根据环境反馈自己决定下一步。

### 传统智能体的五级演进

| 级别 | 核心能力 | 典型样子 |
|---|---|---|
| 简单反射 | 条件-动作规则 | 恒温器 |
| 基于模型 | 维护内部世界模型（引入**记忆**） | 能记住「刚才看到前方有车」 |
| 基于目标 | 为达成目标做规划 | 会绕路 |
| 基于效用 | 在多个冲突目标间**权衡** | 又快又省又安全里的最优解 |
| 学习型 | 从经验中改进 | 越用越好 |

其中两级是后面章节的源头：

- **「基于模型」引入了记忆** → 第 8 章「记忆与检索」的源头
- **「基于效用」引入了权衡** → 今天 Agent 做规划时的基本逻辑

**LLM 那一级是质变，不是量变。** 前五级的能力都来自工程师**显式编写**（规则、模型、效用函数都是人设计的）；LLM 智能体的知识来自**预训练隐式获得**。所以它才能听懂「帮我规划一下厦门之旅」这种模糊指令——换成传统智能体，你得先把「厦门之旅」翻译成规则。

### 分类维度：按决策时机

| 类型 | 特点 |
|---|---|
| 反应式 | 快、短视 |
| 规划式 | 深思熟虑、但慢 |
| 混合式 | 两者结合 |

LLM 智能体的解法很巧妙：**它不当「棋手」，而是把自己变成一连串「规划-反应」的微循环。**

## 二、智能体怎么运作（全书地基）

PEAS 模型 + **Agent Loop**：

```
感知 → 思考 → 行动 → 观察 →（回到感知）
```

落到代码里就是三个字段，这就是智能体和 LLM 之间的「交互协议」：

```
Thought:     用户想知道北京的天气。我需要调用天气查询工具。
Action:      get_weather(city="北京")
Observation: 北京当前天气：Sunny，气温29摄氏度
```

| 字段 | 是什么 |
|---|---|
| `Thought` | 模型的自然语言思考，**不执行**，只是让模型先想清楚 |
| `Action` | 要调用的工具，格式 `函数名(参数=值)`；写成 `Finish[最终答案]` 表示结束 |
| `Observation` | 工具返回的结果，**由代码封装成自然语言**再喂回模型 |

**关键设计：工具返回的原始 JSON 不能直接喂回模型**，要先转成简洁的自然语言。这就是书上说的「感知系统扮演传感器角色」。

这张图是全书所有章节的地基：第 4 章 ReAct、第 7 章自研框架、第 10 章通信协议，全都是给这个循环做工程化。

## 三、代码骨架

```python
# 1. system prompt —— 定角色、工具清单、输出格式
AGENT_SYSTEM_PROMPT = """..."""

# 2. 工具 —— 就是普通 Python 函数
def get_weather(city: str) -> str: ...
def get_attraction(city: str, weather: str) -> str: ...

# 3. 工具注册表 —— 这个字典就是「工具库」
available_tools = {"get_weather": get_weather, "get_attraction": get_attraction}

# 4. 主循环
prompt_history = [system_prompt, user_request]
while True:
    response = llm.chat(prompt_history)      # 模型输出
    prompt_history.append(response)          # 塞回历史
    action = parse(response)                 # 正则解析 Action
    if action.name == "Finish":              # 终止条件
        break
    observation = available_tools[action.name](**action.args)   # 执行工具
    prompt_history.append(observation)       # 观察结果塞回历史
```

## 四、四个设计要点

| # | 要点 | 说明 |
|---|---|---|
| 1 | **system prompt 是「宪法」** | 定三件事：角色、可用工具清单、输出格式。其中「Action 必须在同一行」不是随便写的——后面全靠正则解析，格式一乱整个循环就崩 |
| 2 | **工具 = 普通函数 + 字典注册** | 关键约束：返回值**必须是自然语言字符串**，不能是裸 JSON，因为它要直接拼进 prompt |
| 3 | **正则截断**（第 172–177 行） | 模型经常一口气吐好几组 Thought-Action，而主循环假设「一次只处理一组」。那个 `(?=...)` 前瞻断言的意思是「匹配到下一个 Thought/Action/Observation 之前就停」。**删掉它，工具参数就会被后面多余的文本污染** |
| 4 | **`prompt_history` 是字符串列表** | 存了用户请求、模型输出、Observation 三种东西，每轮 `"\n".join()` 拼成一大坨发回去。**不区分 role**——模型自己说的话被当成「用户说的话」又塞回去了。这是极简写法，能跑，但模型看到的是文本泥巴而不是结构化对话历史。**第 7 章会换成正式的 messages 数组** |

> 这一条是理解前后章节差异的关键。

## 五、实跑结果

`chapter1\demo.py` 跑通，三轮循环：

```
循环 1  查天气   get_weather(city="北京")                      → Sunny，29 摄氏度
循环 2  推景点   get_attraction(city="北京", weather="Sunny")   → 天安门、天坛…
循环 3  结束     Finish[北京今天天气晴朗，气温29摄氏度…]         → 任务完成
```

两个值得注意的观察：

- **Tavily 返回的是英文**（`Under sunny weather, Tiananmen Square, Temple of Heaven...`），模型照样把它整合成中文回答。这实证了本章那条设计原则——**Observation 只要是自然语言，模型就能消化，不要求语言一致、也不要求结构化**。
- **每个工具只被调用了一次**，没有重复。这是 Thought 起作用的地方：模型在思考阶段就规划好了「先查天气、再推荐景点」，不是盲目试错。
