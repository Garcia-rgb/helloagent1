## 1. 知识骨架

第 3 章在回答一个问题：**智能体的大脑是怎么工作的**。它按「由简到繁」排了四节：

### 3.1 语言模型与 Transformer

**3.1.1 从 N-gram 到 RNN**

N-gram 是最朴素的思路：算「一句话出现的概率」= 把每个词出现的条件概率连乘。

```
P(datawhale agent learns)
  = P(datawhale) × P(agent|datawhale) × P(learns|agent)
  = 2/6 × 2/2 × 1/2 = 0.167
```

核心假设是**马尔可夫假设**——第 n 个词只跟前 n-1 个词有关。这是它的天花板：n 一调大，参数数量指数爆炸；n 一小，就看不见长距离依赖。而且它完全不理解语义，`agent` 和 `robot` 在它眼里毫无关系。

**词向量**是第一次「理解语义」的尝试：把词映射成向量，让语义关系变成向量运算。经典例子是 `king - man + woman ≈ queen`——语义的「加减法」。

**3.1.2 Transformer 架构**

RNN 的死穴是**串行**：第 5 个词必须等第 4 个算完。Transformer 用**自注意力**把整句话一次性摊开算，因此可以并行。代价是丢了顺序信息，所以要额外加**位置编码**。

教程这一节的代码是手写一个完整 Transformer（含 Encoder / Decoder 核心层）。

**3.1.3 Decoder-Only 架构**

完整 Encoder-Decoder 适合「输入一篇文章、输出一篇翻译」这种 seq2seq 任务。但 GPT 系证明：**只要一个 Decoder 也够了**——把任务都改写成「续写」形式即可。结构更简单、更省参数、更容易规模化，所以现在主流 LLM 全是 Decoder-Only。

### 3.2 与大语言模型交互

**3.2.1 提示工程**——Zero-shot / Few-shot / Chain-of-Thought。CoT 的价值在于让模型把中间推理步骤写出来，把「隐式计算」变成「显式 token」，准确率显著上升。

**3.2.2 文本分词**——为什么不能用「字符」或「单词」做输入单元：

- 字符级：序列太长，模型要花大量注意力去重建词
- 单词级：词表爆炸，且遇到未登录词（OOV）就没辙

**BPE（字节对编码）**是折中方案：从字符出发，反复把「共现频率最高的相邻单元」合并成一个新单元。这样常见词变成 1 个 token，罕见词拆成子词，词表规模可控（Qwen 是 151936）。

教程特别提醒了分词对智能体的三个实际影响：**上下文窗口按 token 算**（不是字符）、**API 按 token 计费**、**模型怪表现的根源常常是分词**（`2+2` 和 `2 + 2` 可能被切成完全不同的 token 序列）。

**3.2.3 调用开源大语言模型**——本章唯一需要下载大文件的一节，用 `transformers` 在本地跑 Qwen。见下面第 3 节详述。

**3.2.4 模型的选择**——从性能、成本、延迟、上下文窗口、部署方式、生态、可微调性、安全伦理八个维度权衡。闭源模型开箱即用，开源模型自主可控。

### 3.3 缩放法则与局限性

**缩放法则**：在对数-对数坐标系下，模型性能（Loss）与参数量、数据量、计算量呈平滑幂律关系。

**Chinchilla 定律**是对「越大越好」的修正：给定算力预算，参数量和训练数据量有最优配比。700 亿参数的 Chinchilla 用比 GPT-3（1750 亿）多 4 倍的数据训练，性能反超。

**能力涌现**：规模过某个阈值后，模型会突然具备小模型完全没有的能力（CoT、指令遵循、多步推理、代码生成）。这是智能体存在的前提。

**模型幻觉**分三类（事实性 / 忠实性 / 内在），缓解手段主要在推理与生成层：RAG、多步推理与验证、引入外部工具。**这三条恰好就是后面第 8、9 章的主题。**

### 2.1 `N_gram.py` —— 纯标准库

```python
corpus = [
    "datawhale agent learns",
    "datawhale agent works",
    "datawhale agent learns",
    "datawhale agent works",
    "datawhale agent works",
    "datawhale agent learns"
]

words = " ".join(corpus).split()
```

其中：

- `corpus` —— 6 句迷你语料，每句 3 个词，共 18 个 token
- `" ".join(corpus)` —— 把 6 句拼成一个大字符串
- `.split()` —— 按空格切成词列表，长度 18
- 后面三步分别算 `P(datawhale)`、`P(agent|datawhale)`、`P(learns|agent)`，最后连乘

实跑输出（与教程文档逐字一致）：

```
第一步: P(datawhale) = 2/6 = 0.333
第二步: P(agent|datawhale) = 2/2 = 1.000
第三步: P(learns|agent) = 1/2 = 0.500
最后: P('datawhale agent learns') ≈ 0.333 * 1.000 * 0.500 = 0.167
```

注意分母是 **6（句子数）** 而不是 18（词数）——代码统计的是「以 datawhale 开头的句子占比」，这是它的简化写法。

### 2.2 `BPE.py` —— 纯标准库

```python
words = {'h u g </w>': 1, 'p u g </w>': 1, 'p u n </w>': 1, 'b u n </w>': 1}
```

其中：

- 键 —— 一个词被切成「字符 + 空格」的形式
- `</w>` —— 词尾标记。用来区分「ug 出现在词中」和「ug 出现在词尾」
- 值 —— 该词的频次

算法循环三步：**统计所有相邻字符对 → 找频次最高的 → 合并**。

实跑输出：

```
第1次合并: ('u', 'g') -> ug
新词表（部分）: ['h ug </w>', 'p ug </w>', 'p u n </w>', 'b u n </w>']
第2次合并: ('ug', '</w>') -> ug</w>
第3次合并: ('u', 'n') -> un
第4次合并: ('un', '</w>') -> un</w>
```

第 1 步为什么选 `(u, g)` 而不是 `(u, n)`：`ug` 在第 1、2 个词里各出现一次，`un` 在 `p u n` 里出现一次但 `(u, n)` 这个**相邻对**只出现 1 次……实际是 4 个词里 `u` 后面分别是 `g`、`g`、`n`、`n`，各 2 次，平局时按遍历顺序取先出现的。

### 2.3 `Word_Embedding.py` —— 需要 numpy

```python
man = np.array([1.0, 1.0])
woman = np.array([2.0, 1.0])
king = np.array([1.0, 2.0])
queen = np.array([2.0, 2.0])

result = king - man + woman
```

其中：

- 四个二维向量 —— 每个词的「语义坐标」，手写死的不是训练出来的
- `king - man` —— 得到「性别之外的王室属性」方向
- `+ woman` —— 沿这个方向换成女性
- 后面用余弦相似度算 `result` 和 `queen` 的接近程度

实跑输出：

```
king - man + woman 的结果向量: [0.9 0.2]
该结果与 'queen' 的相似度: 1.0000
```

注意：算出来的 `[0.9, 0.2]` **并不等于** `queen` 的 `[2.0, 2.0]`——但**方向完全一致**，所以余弦相似度是 1.0000。这正是词向量的用法：**关心方向，不关心长度**。

### 2.4 `Transformer.py` —— 需要 torch

完整的 Transformer 实现：位置编码 → 多头注意力 → 前馈网络 → 残差连接与层归一化 → 编码器层 → 解码器层。

实跑输出：

```
模型输出的形状: torch.Size([2, 12, 5000])
```

其中：

- `2` —— batch size，一次喂 2 条序列
- `12` —— 序列长度，每句 12 个 token
- `5000` —— 词表大小，输出是每个位置上「5000 个词各自的得分」

**`[2, 12, 5000]` 是理解所有 LLM 的钥匙**：模型每读一个位置，都在算「下一个词是词表里哪个词」。`generate()` 就是把这个过程重复 N 次。

## 3. 本地部署 Qwen1.5-0.5B-Chat

### 3.1 为什么不能照教程原样跑

教程 `code/chapter3/Qwen.py` 第 1-3 行：

```python
import os
os.environ["HF_ENDPOINT"] = "https://hf-mirror.com"
```

它把下载源指向了 hf-mirror.com。但实测这台机器上：

| 域名 | 结果 |
|---|---|
| `huggingface.co` | 不可达 |
| `hf-mirror.com` | 不可达 |
| `www.modelscope.cn` | **可达** |

整条 HuggingFace 链路（含国内镜像）都不通。所以模型权重要从 **ModelScope** 拉。

### 3.2 部署所需资源（本机实测）

| 资源 | 需求 | 本机实测 |
|---|---|---|
| 磁盘 | 模型 1.2 GB + 依赖约 300 MB | D 盘可用 436.2 GB |
| 内存 | 权重 1.73 GB（float32）/ 0.86 GB（bfloat16）+ 激活开销 | 总 15.6 GB，运行时空闲 3.7 GB |
| CPU | 无需 GPU，纯 CPU 可跑 | 12 逻辑核 Intel64 Family 6 Model 186 |
| GPU | 可选。有则自动切 `cuda` | **无 CUDA，走 CPU** |
| 网络 | 仅下载时需要；**推理完全离线** | 走 ModelScope |

**结论：一台普通 Windows 笔记本就能跑，不需要显卡。** 代价是速度——实测 8.7 tok/s，也就是每秒输出约 9 个字。

### 3.3 部署步骤

**第 1 步：装依赖**


本机踩的坑：`torch` 走 PyPI（清华源）拿到的 **Windows wheel 就是 CPU 版**，118 MB、2.4 MB/s；而 pytorch 官方源同样文件只有 **0.12 MB/s**，慢 20 倍。所以**不要**加 `--index-url https://download.pytorch.org/whl/cpu`。

**第 2 步：下载模型权重**


这个脚本直连 ModelScope 的文件 API，不依赖 `modelscope` SDK，也不需要 HuggingFace：

```python
def make_session():

    s.trust_env = False          # 关掉环境代理，避免被沙箱/系统代理劫持
```

其中：

- `s.trust_env = False` —— 忽略 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量。本机沙箱会注入代理，不关掉会 502
- 下载支持**断点续传**：记录已下载字节数，用 `Range: bytes=N-` 请求剩余部分

### 3.5 与教程 `Qwen.py` 的 6 处差异

本地化副本是 `chapter3\demo.py`，**教程原文件一个字没动**。差异全部集中在「模型从哪来」和「CPU 适配」：

```python
# ① 模型来源：网络 ID → 本地路径
model_id = os.path.join(REPO_ROOT, "models", "Qwen1.5-0.5B-Chat")

# ② 切断联网，确保用的是本地文件
os.environ["HF_HUB_OFFLINE"] = "1"
os.environ["TRANSFORMERS_OFFLINE"] = "1"

# ③ 教程那行 hf-mirror 端点删掉了（不可达）
# os.environ["HF_ENDPOINT"] = "https://hf-mirror.com"

# ④ 显式 float32（教程默认 bfloat16）
model = AutoModelForCausalLM.from_pretrained(model_id, dtype=torch.float32).to(device)

# ⑤ 显式传 attention_mask + no_grad
with torch.no_grad():
    generated_ids = model.generate(
        model_inputs.input_ids,
        attention_mask=model_inputs.attention_mask,
        max_new_tokens=512,
    )
```

其中：

- ① `model_id` —— 传本地目录时，`from_pretrained` 直接读磁盘，不发网络请求
- ② 两个 offline 开关 —— 双保险，防止 transformers 偷偷去 Hub 检查版本
- ④ `dtype=torch.float32` —— checkpoint 存的是 BF16，CPU 上 bf16 运算**远慢于** float32。代价是权重从 0.86 GB 涨到 1.73 GB。**如果内存紧张就改回 `torch.bfloat16`**
- ⑤ `attention_mask` —— 教程没传，会有 warning；`torch.no_grad()` 关掉梯度计算，省内存

## 4. 一个值得记的实测发现：参数量对不上

校验时出现了两个不一致的数字：

| 来源 | 参数量 |
|---|---|
| safetensors 文件内 | 619,570,176 |
| 加载后的模型 | 463,987,712 |
| 差值 | 155,582,464 |

差值刚好等于 `151936 × 1024 = 155,582,464`，即 **词表大小 × 隐藏维度**。

原因在 `config.json` 的 `tie_word_embeddings = True`：**输入嵌入层和输出层共享同一份权重**。checkpoint 里 `embed_tokens.weight` 和 `lm_head.weight` 各存了一份，加载后 PyTorch 把它们指向同一个张量，所以只算一次。

这是小模型的常规省参数手段——单这一项就省下 25% 的参数量。
